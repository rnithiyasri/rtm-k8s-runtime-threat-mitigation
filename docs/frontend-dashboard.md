# RTM Operational Dashboard & Threat Injection Documentation

## Overview

The **RTM Operational Dashboard** provides real-time observability and controlled runtime adversary emulation for the Runtime Threat Mitigation engine in Kubernetes. It bridges kernel-level detection telemetry from Falco with automated containment decisions evaluated by the controller.

---

## 1. Dashboard Architecture & Features

1. **Pipeline Strip (7 Stages)**:
   - **Stage 1 (Attack Trigger)**: Controlled attack scenario injection (or human-in-the-loop emulation).
   - **Stage 2 (Falco eBPF Detect)**: Highlights when an alert has been generated by the kernel eBPF probe.
   - **Stage 3 (Falcosidekick Forward)**: Shows webhook forwarding to controller.
   - **Stage 4 (Controller Receive)**: Shows alert receipt and timestamp ingestion into ring buffer.
   - **Stage 5 (Dedupe & Decide)**: Confirms alert deduplication (10s window) and graduated policy state evaluation.
   - **Stage 6 (Safety Gate)**: Evaluates namespace opt-in label barrier (`rtm.enforce=true`) and `DRY_RUN` mode. Displays warning if blocked by a safety gate.
   - **Stage 7 (Mitigation Action)**: Confirms whether `isolate_network` (NetworkPolicy restriction) or `kill_pod` was executed.

2. **INJECT THREAT Interactive Panel**:
   - Four scenario buttons arranged in a 2-column responsive desktop grid:
     * **E1 — Shell**: Subtitle: `kubectl exec sh` &middot; Expected detection: `RTM-001`.
     * **E2 — Token Read**: Subtitle: `fires RTM-001 + RTM-003` &middot; Expected detection: `RTM-001` + `RTM-003`.
     * **E3 — Binary in /tmp**: Subtitle: `RTM-005` &middot; Expected detection: `RTM-005`.
     * **E4 — Reverse Shell**: Subtitle: `RTM-007` &middot; Expected detection: `RTM-007`.
   - **4-Stage Correlation Status Card**:
     * Stage 1 (`Simulate`): Shows execution duration and unique simulation ID (`sim-xxxxxxxx`).
     * Stage 2 (`Falco Detect`): Correlates incoming alerts independently from `/alerts/recent` with a 14s bounded timeout.
     * Stage 3 (`RTM Decision`): Displays planned decision (`alert_only`, `isolate_network`, `kill_pod`).
     * Stage 4 (`Safety Gate`): Displays whether the action was executed or blocked by safety gate / `dry_run_env=true`.
   - **Manual Terminal Reference**: Collapsible drawer with copyable `kubectl exec` commands for manual validation.

3. **Live Alert History Table**:
   - Queries `GET /alerts/recent` on the controller.
   - Columns: `Time`, `Rule ID`, `Pod`, `Priority`, `Hint`, `Dedupe`, `Mode (Dry/Live)`, `Gate`, `Action Taken`, `Gate Reason`.
   - Flashes incoming alert rows dynamically upon receipt.

4. **Monitored Workloads (Pod Grid)**:
   - Queries `GET /pods/status?namespace=shop`.
   - Cards display pod name, phase (`Running`, etc.), restart counts, and status pills (`rtm.enforce=true`, `rtm.tier=restrict`).

5. **Live Controller Config Banner**:
   - Queries `GET /config`.
   - Displays active `STRATEGY` (`graduated`, `detect_only`, `always_delete`), `DRY_RUN` state (`true`/`false`), and `ENFORCE_LABEL_SELECTOR`.

## 2. Threat Simulation API Contract

### Endpoints

#### `GET /simulate/scenarios`
Returns metadata for all available predefined threat simulations.

#### `POST /simulate`
Triggers a controlled threat simulation on the designated test workload (`shop/victim`).

**Request Payload:**
```json
{
  "scenario": "E1"
}
```

**Allowed Scenarios:** `E1`, `E2`, `E3`, `E4` (case-insensitive).

**Response Payload (200 OK):**
```json
{
  "status": "completed",
  "simulation_id": "sim-33b14305",
  "scenario": "E1",
  "scenario_name": "Shell",
  "subtitle": "kubectl exec sh",
  "expected_rules": ["RTM-001"],
  "target": {
    "namespace": "shop",
    "pod": "victim-6b765ff685-7788t",
    "container": "victim"
  },
  "executed_at": 1792771348.682,
  "duration_s": 0.109,
  "message": "Simulation E1 completed successfully in shop/victim-6b765ff685-7788t. Awaiting Falco detection."
}
```

**Error Responses:**
- `400 Bad Request`: Invalid scenario identifier (e.g., `E5` or arbitrary command injection attempts).
- `409 Conflict`: Simulation already in progress (concurrency lock active).
- `503 Service Unavailable`: Kubernetes client unavailable or victim pod not found in namespace `shop`.

## 3. Security & Safety Invariants

1. **Fixed Scenario Mappings (Zero User Command Injection)**:
   - The API accepts only the exact strings `E1`, `E2`, `E3`, `E4`.
   - Commands are strictly server-side constants. Arbitrary commands, executable paths, or arguments from the browser are rejected.
2. **Workload Isolation & Namespace Restriction**:
   - Execution is hardcoded to namespace `shop` and pods matching label `app=victim`.
   - Production / application workloads (`auth-service`, `frontend`, `order-service`, `payment-service`) cannot be targeted.
3. **No Synthetic Alerts**:
   - `/simulate` only executes the command inside the test container and returns execution telemetry.
   - Real alerts are detected exclusively via the kernel eBPF probe &rarr; Falco &rarr; Falcosidekick &rarr; Controller webhook pipeline.
4. **Credential & Secret Protection**:
   - E2 (`Token Read`) redirects output to `/dev/null` (`cat ... > /dev/null`). ServiceAccount credentials are never retrieved, captured, or returned over the API.
5. **Reverse Shell Safety**:
   - E4 (`Reverse Shell`) simulates the shell network connection pattern against `127.0.0.1:4444` (immediate connection refused) without establishing a real reverse shell, providing interactive shells, or enabling unauthorized remote access.
6. **Enforcement Safety Gate**:
   - `DRY_RUN=true` remains the default. Graduated response decisions evaluate normally, but live mutations (`isolate_network`, `kill_pod`) are blocked by the safety gate.
7. **Least-Privilege RBAC**:
   - Controller uses `Role` `rtm-controller-role` scoped to namespace `shop` granting `pods` (`get`, `list`, `patch`, `delete`) and `pods/exec` (`create`, `get`). Broad cluster-admin privileges are not required.
